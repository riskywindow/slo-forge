# Continuum security and privacy

Continuum execution state can contain prompts, generated tokens, KV tensors,
recurrent state, sampler state, guided-decoding state, workflow results, and client
delivery cursors. Treat a capsule and every referenced chunk as sensitive tenant
data, even when the tensor values are not directly human-readable.

## Trust boundaries

- The logical and physical state schemas are untrusted inputs until strict schema,
  size, compatibility, ownership-epoch, and integrity checks pass.
- Runtime adapters are version-scoped trust boundaries. An adapter is authorized
  only for the tenant, session, runtime build, and operation in its capability
  contract. Raw runtime pointers, handles, descriptors, and allocator internals are
  never portable capsule state.
- Generated conversion code is untrusted until its output is independently checked
  against the trusted reference converter for the declared shapes, layouts,
  exactness class, and bounded continuation horizon. Generated code does not
  receive storage encryption keys.
- The ownership coordinator and gateway token ledger authorize state mutation and
  client-visible output. A valid capsule does not itself grant permission to
  resume, fork, or emit tokens.
- Storage and transport move bytes. They do not decide model compatibility or
  ownership.

## Tenant isolation and authorization

Content-store keys are scoped by `(tenant_id, digest)`. Cross-tenant deduplication
is disabled by default, so equal chunks in different tenants occupy independent
authorization namespaces. Manifests cannot reference another tenant's chunks.
This reduces equality leakage through the store; it does not make exported hashes
or capsule metadata public.

Every capture, read, resume, migration, fork, and clone must be authorized for its
tenant and session before bytes are exposed. A fork creates new session identity
and owner epochs; shared immutable chunks do not share mutation or output rights.
Adapters receive a narrowly scoped operation context rather than inherited process
credentials. Secrets must be removed from adapter and converter subprocess
environments.

## Encryption at rest

`AuthenticatedEncryptedStore` is an optional fail-closed wrapper around a local
`ContentStore`. It uses AES-256-GCM from the optional `cryptography` package. If the
package or AES-GCM implementation is unavailable, construction fails with a typed
`CryptoUnavailable` error; plaintext storage is not selected automatically.

For each encrypted chunk:

- the key provider must return exactly 32 bytes for an explicit key ID;
- a fresh 96-bit nonce is generated by the operating-system CSPRNG;
- tenant ID, capsule ID, state version, key ID, plaintext digest, plaintext size,
  and schema version are authenticated as associated data;
- the underlying store contains only ciphertext and an AEAD tag;
- the portable encrypted reference contains a key ID, never key bytes;
- read authorization binds tenant, capsule, a minimum accepted state version, and
  allowed key IDs;
- metadata modification, ciphertext modification, and cross-context chunk
  substitution fail authentication;
- a state version below the caller's coordinator-backed watermark fails as a stale
  replay.

The bundled static key provider is for deterministic tests and isolated offline
deployments. Production systems should implement the key-provider interface with a
KMS or secret manager, enforce rotation and revocation outside capsule metadata,
and keep encryption keys out of reports, logs, crash dumps, runtime adapters, and
generated kernels.

Authenticated encryption does not replace capsule authorization, transaction-ID
uniqueness, fencing tokens, or owner-epoch validation. A copied current ciphertext
and its reference remain valid until access policy or retention revokes them.

## Encryption in transit

The portable `tcp_v1` transport uses a versioned length-prefixed protocol with:

- bounded headers, chunks, transfer size, retries, replay history, and deadlines;
- SHA-256 chunk checksums and per-chunk acknowledgments;
- a receiver-owned destination store;
- a fixed tenant policy at the listener;
- direction-scoped HMAC-SHA-256 authentication over setup, every chunk identity,
  acknowledgment, rejection, and completion message using a key that never
  crosses the connection;
- transfer-ID binding on chunk and acknowledgment frames, preventing a captured
  authenticated frame from being substituted into another transaction;
- optional AES-256-GCM payload encryption with deterministic transfer/sequence/
  attempt-scoped nonces and AAD binding the plaintext digest and size;
- durable, bounded rejection of completed transfer-ID replay;
- stale sequence and chunk-identity substitution checks;
- explicit failure on truncation, timeout, corruption, unauthorized tenant, and
  replay, with no fallback transport.

Bare `tcp_v1` advertises `supports_encryption=false`: frame authentication does not
hide state bytes. Supplying an explicit 256-bit payload key at both endpoints
selects `tcp_v1_aes256gcm`, advertises encryption, and prohibits downgrade; wrong
keys and modified ciphertext fail authentication. This mode supplies payload
confidentiality but not certificate-backed peer identity, so non-local production
deployments should still use mutually authenticated TLS, a secured service mesh, or
an approved encrypted network. The in-process and local-file transports make no
encryption claim.

## Integrity, replay, and ownership

Chunk hashes authenticate content identity; AEAD binds encrypted content to its
authorization context; capsule Merkle roots bind manifests and evidence; and the
transaction journal binds ownership transitions. These checks are complementary.
A caller must reject:

- a missing or corrupt chunk;
- a capsule with a mismatched Merkle root or model/tokenizer compatibility domain;
- a state version older than the accepted transaction watermark;
- a reused completed transaction or transfer identifier;
- a runtime action carrying a stale owner epoch or fencing token;
- output from any epoch other than the gateway's expected owner epoch.

The local TCP replay journal uses SQLite with WAL, full synchronization, and a
configured maximum entry count. Its retention bound must cover the deployment's
maximum replay window. Distributed deployments should bind replay decisions to
the durable transaction coordinator instead of treating a node-local journal as a
global authority.

## Logging and observability

Never log state payloads, plaintext samples, encryption keys, authorization keys,
nonces paired with ciphertext, prompt/token content, workflow results, or raw
adapter exceptions that may include state. Events may include tenant-safe opaque
identifiers, sizes, hashes where policy permits, schema versions, state versions,
owner epochs, bounded error classes, and measured timings. Public reports should
use redacted tenant/session identifiers and artifact provenance.

Metrics and crash handling must avoid payload previews. Core queues, protocol
frames, diagnostic error buffers, retries, and subprocesses are bounded. TCP
listener diagnostics retain only a bounded error class and static reason; they do
not include frame payloads or credentials.

## Retention and deletion

Capsules and chunks require explicit TTL and retention policy. Garbage collection
removes expired, unreferenced metadata before unlinking local files. Fork and clone
reference counts must reach zero before collection. Encryption-key revocation can
make retained ciphertext unreadable but is not a substitute for retention policy.
TCP receiver staging chunks receive a bounded TTL so interrupted, unpublished
transfers remain collectible. Local store directories and metadata use private
owner-only modes, recorded paths are checked against their canonical tenant scope,
file reads are bounded and reject symlinks where the platform supports
`O_NOFOLLOW`, and compressed input has a hard expansion bound.

Continuum provides best-effort logical deletion, not guaranteed physical secure
erasure. Filesystems, SSD wear leveling, copy-on-write snapshots, backups, object
store versions, caches, and replicas may retain old blocks after unlink. Operators
must use storage-layer encryption, lifecycle controls, backup deletion, and media
sanitization appropriate to their threat model. Reports must never claim stronger
deletion guarantees.

## Deployment checklist

1. Bind every operation to tenant, session, purpose, transaction, and current owner
   epoch.
2. Keep cross-tenant deduplication disabled.
3. Use a KMS-backed encryption key provider and an encrypted transport channel.
4. Restrict listener addresses and firewall ingress; never publish bare `tcp_v1`.
5. Configure bounded replay retention, state TTLs, and transaction retention.
6. Verify capsule integrity and semantic compatibility before allocating or
   importing destination state.
7. Fence stale sources before accepting destination output.
8. Redact logs and reports; audit adapter and converter subprocess environments.
9. Validate generated conversion code independently before execution.
10. Exercise corruption, replay, stale epoch, unauthorized fork/resume, coordinator
    restart, and deletion procedures with deterministic fault seeds.
